# Commit & Push

Generate a commit message from the current diff, commit, and push to the current branch.

## Workflow

### 1. Gather context

Run these in parallel:

- `git status` — see untracked and modified files
- `git diff` and `git diff --cached` — see all changes (staged + unstaged)
- `git log --oneline -10` — recent commits for message style reference
- `git branch --show-current` — confirm the current branch

### 2. Review changes

- Scan the diff for secrets, credentials, `.env` files, or large binaries. **Warn the user and exclude them** before proceeding.
- If there are no changes to commit, tell the user and stop.

### 3. Stage files

- Stage files by name — **never use `git add -A` or `git add .`**.
- Skip files that look like secrets or build artifacts.
- If unsure whether a file should be included, ask the user.

### 4. Write commit message

- Follow the style of recent commits in the repo (from step 1).
- If no clear style exists, use [Conventional Commits](https://www.conventionalcommits.org/) format: `type(scope): description`.
- Keep the subject line under 50 characters, lowercase, no period at the end.
- Add a body only when the "why" isn't obvious from the subject. Use bullet points to summarize what was updated.
- **Never** include `Co-Authored-By`, `Generated by`, or any other AI/assistant attribution in the commit message.
- Always pass the message via HEREDOC to preserve formatting.

#### Allowed types

| Type     | Description                           |
| -------- | ------------------------------------- |
| feat     | New feature                           |
| fix      | Bug fix                               |
| chore    | Maintenance (e.g., tooling, deps)     |
| docs     | Documentation changes                 |
| refactor | Code restructure (no behavior change) |
| test     | Adding or refactoring tests           |
| style    | Code formatting (no logic change)     |
| perf     | Performance improvements              |

#### Example

```
feat(auth): add JWT login flow

- Implemented JWT token validation logic
- Added documentation for the validation component
```

### 5. Confirm with user

Present the proposed commit message and ask the user to choose:

1. **Use as-is** — proceed to commit
2. **Edit** — user provides corrections, then proceed

Do **not** commit until the user explicitly approves.

### 6. Commit

```bash
git commit -m "$(cat <<'EOF'
type(scope): subject line

Optional body explaining why.
EOF
)"
```

- If a pre-commit hook fails, fix the issue, re-stage, and create a **new** commit (never `--amend`).

### 7. Push

- Push to the current branch: `git push origin HEAD`
- If the branch has no upstream, use `git push -u origin HEAD`.
- If push is rejected (non-fast-forward), inform the user and ask how to proceed — **never force push**.

### 8. Confirm

Show the user the commit hash, message, and the branch it was pushed to.

## Rules

- **Never** include any AI/assistant attribution (e.g. `Co-Authored-By`, `Generated by AI`, etc.) in commit messages or anywhere in the git history.
- Never use `--force`, `--no-verify`, or `--no-gpg-sign`.
- Never push to `main` or `master` without explicit user confirmation.
- Never amend an existing commit unless the user explicitly asks.
- If the current branch is `main`/`master`, warn the user and ask if they want to create a feature branch instead.
